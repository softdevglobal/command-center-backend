# Sophie Text Test

Command Center → Agents & Performance → Sophie Text Test opens a real text conversation using the existing business MCP integrations. There is no mock mode in this screen. Booking and signup submissions create real records, and account setup can send real SMS/email notifications. The user acknowledges this before starting and confirms the actual booking/signup details during the conversation.

## Local setup

```env
AI_TEXT_TEST_ENABLED=true
OPENAI_API_KEY=<backend OpenAI API key>
# Optional; defaults to the existing Luna text model:
AI_TEXT_TEST_MODEL=gpt-6-luna
# Optional; defaults to this backend's loopback address and PORT:
AI_TEXT_TEST_MCP_ORIGIN=http://127.0.0.1:5050
```

The local dashboard adds `/api/ai/text-test` to its existing `VITE_LOCAL_API_PATHS` list. Restart the backend and Vite if the screen or endpoint is not available after updating the environment.

The screen is limited to signed-in super admins. `AI_TEXT_TEST_ENABLED` is separate from voice settings. Existing product MCP flags, dedicated AI identities, mapping checks and write flags still apply; the text screen does not enable or bypass them.

## Real tools

Receptionist mode resolves the selected DID through the existing queue/product mapping and uses a dedicated MCP SDK client for `/api/bms-black/ai/mcp`, `/api/bms-blue/ai/mcp` or `/api/bms-pink/ai/mcp`. Its business profile, service, availability and creation tools come from that endpoint's actual tool inventory. The DID's initial owner/branch/queue is checked before each tool call. Booking request keys are private, generated by the server and reused rather than supplied by the model.

Business onboarding mode uses the configured onboarding number, its separate bridge credential and the existing `/api/ai/mcp/onboarding-call` endpoint. Sophie asks whether the user wants Black, Pink or Trade, saves a call-bound draft and uses the existing confirmed account-creation workflow. Text tests use their own random onboarding call IDs and never reuse a customer call's draft.

Business questions are answered from the verified MCP profile and service tools. Unsupported facts are unknown; the assistant must not invent policies, prices, availability or a handoff. Current branch-local date and time are supplied for relative date requests.

## API

- `GET /api/ai/text-test/options`
- `POST /api/ai/text-test/sessions` — `{mode, did, brand?, acknowledgeRealActions:true}`
- `POST /api/ai/text-test/sessions/:id/messages` — `{messageId:<stable UUID>, text}`
- `POST /api/ai/text-test/sessions/:id/end`

Every endpoint authenticates the administrator. Sessions belong to the administrator who started them. A stable message ID recovers the same response after transport retries and cannot be reused with different text. Concurrent new messages are rejected while a reply is pending.

## Model and lifetime

Only Start test and submitted chat turns request model responses. The implementation uses the [Responses API function-calling flow](https://developers.openai.com/api/docs/guides/function-calling) with `store:false`, serial tool calls, and server-owned conversation history. All returned reasoning/output items are replayed for continuation; private reasoning is never sent to the dashboard. The UI shows cumulative request and token counts, plus expandable actual tool results.

End test aborts pending text-model work, terminates the test's MCP session and releases its in-memory history. Already-submitted bookings/accounts remain real records. Closing this screen also attempts cleanup. Idle text tests expire after 15 minutes; the maximum text session lifetime is one hour. These limits belong only to the new text-test service.

This implementation does not open Asterisk, SIP, audio, a microphone or a voice model. It does not alter voice bridge files, customer call routing, voice prompts or customer call session limits.

## Verification

`node --import tsx --test tests/ai-text-test.test.ts` checks permission gates, owner isolation, real tool dispatch, complete tool-result continuation, replay protection, text startup restrictions, interrupted requests and cleanup. External providers are substituted only inside automated tests. Live smoke checks use actual model responses and read-only business tools; the automated verification does not submit customer bookings or create owner accounts.

In production, use one backend replica or session affinity for these ephemeral text sessions. A backend restart ends active text conversations; it does not delete real records already submitted.
